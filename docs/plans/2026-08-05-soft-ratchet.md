# soft-ratchet-exceeded: soft 警告の規則ID別ラチェット（2026-08-05・提案③）

> **状態: 提案（未実装）**。採用先実測の監査で露出した欠陥への対策3件のうちの1件。
> 実装時に §10 の Phase として採番し、本文書へ実施結果を追記する。

## 背景

採用先の実測で **soft 警告 164 件が正常化したノイズ**になった。soft の設計前提は
「理由があれば 1 回の見送りは可・無理由の放置は歯止めが塞ぐ」だが、現行の歯止めは
`chronic-soft-violation`（Phase 63）のみで、次の 3 つの穴がある:

1. 対象が `file-too-long` / `dir-too-crowded` の 2 規則・**箇所単位**に限られる。
2. 土台がローカルの違反ログ（`.guardrails/violations.jsonl`・gitignore 済み）のため、
   **CI・新規 clone では不発**——最終防衛線が総量の漸増を見ていない。
3. 「同一箇所の放置」は見るが「**総量のゆでガエル**」（1 件ずつ増えて 164 件）は
   どの門も見ていない。

保留タスク「効果の評価設計」（soft 無視率の計測）は計測であって歯止めではない——
計測と別に、増加そのものを可視化して止める機構を足す（G9: 沈黙の禁止）。

## 検討した2案

1. **グローバル総量上限案**: soft 全体に 1 つの閾値。実装は最軽量だが、ある領域の
   解消が別領域の増加を**相殺で隠す**（164 のまま中身が入れ替わる）。不採用。
2. **規則ID別ラチェット案（採用）**: 追跡ファイルに規則IDごとの許容件数を持ち、
   規則IDごとに超過を検出する。「領域別」の領域＝規則ID。相殺が効かず、警告 1 行が
   「どの規律が緩んでいるか」をそのまま指す（G4: 1違反1行・規則ID）。

## 設計

- ベースラインの正本: `.guardrails/soft_baseline.json`（**git 追跡**——CI でも効かせる。
  形式は `{"規則ID": 許容件数}` のみの平坦な辞書）。
- 生成・更新の唯一の主体は `dev.py ratchet`（現在の soft 実測件数で書き出す。
  手編集はしない——`generate_structure.py` と同型の「生成物だが追跡する」運用）。
- `check_structure.py` の末尾（全 soft 出揃い後——`chronic-soft-violation` と同じ
  呼び出し順の保証を使う）で規則ID別に集計し、baseline と比較:
  - **超過** → `SOFT:soft-ratchet-exceeded`（規則IDごとに 1 行。
    `file-too-long 12→15` の形で差分を示す——164 行のノイズを「増えた領域だけの
    数行」に圧縮するのが狙い）。
  - **減少** → 情報行で `dev.py ratchet` による引き下げを促す（自動では書き換えない。
    検査器が追跡ファイルを書き換えると diff が検査のたびに動く）。
  - **baseline 不在** → `SOFT:soft-ratchet-unbaselined` 1 行（`binding-unstamped` と
    同じ「見える猶予」。不発を静かにしない——本キットの監査で「検査の定義域が静かに
    空になる」と指摘された型を、新設する検査自身が持たないようにする）。
- **キット原本には実測値で充填した baseline を同梱**する（原本の正常状態は SOFT 5 件
  ——§3.3「出荷状態の想定出力」の値をそのままピンにする）。導入先では Step 3（フック
  導入）の直後に `dev.py ratchet` を 1 回実行する手順を BOOTSTRAP.md に追記する。
- **意図的な増加**（正当な理由での 500 行超え等）は、baseline の引き上げを**同一
  コミットに同梱**することで通す——見送りの理由が diff とレビューに可視化される。
  守りが緩む方向の変更は無記録で行わない（GOALS「降格の統治」と同じ非対称）。
- **soft 導入**。ラチェットの比較自体は決定的だが、運用摩擦（正当な増加の頻度・
  baseline 更新の儀式化リスク）が未実測（GOALS 非対称閾値②。前例:
  `feat-without-plan` soft→hard）。hard 昇格の判断材料は違反ログ（§3.6）で計数する。

## 対象外として明記する範囲

- **箇所の入れ替わりに盲目**: 1 件解消＋1 件新規＝件数横ばいは検出しない。箇所単位の
  放置は `chronic-soft-violation` の持ち場であり、重複登録しない（G5）。2 つの検査は
  「箇所の慢性化」×「総量の漸増」の直交する 2 軸として併存する。
- soft 警告の**中身の妥当性**（その 500 行超えが正当か）は判定しない——本検査が
  強制するのは「増加が diff に見える」ことまで。

## 違反注入コーパスの扱い

キット原本に baseline を同梱すると、ランナーの「既存パスは SKIP(exists)」設計により
baseline 注入ケースは原本上で SKIP になる。`file-too-long` 注入（既存ケース）との
合成で発火させられるか（注入 1 件で原本 baseline を超過させられるか）を実装時に検証し、
不能ならコーパス対象外分類（Phase 47 の 5 分類）へ理由を記載する。初回 DoD は
baseline を実測値未満に一時改変して落ちるのを見る手動注入で行う。
