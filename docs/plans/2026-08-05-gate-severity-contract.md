# gates-severity-drift: 台帳の severity 宣言と実装の双方向照合（2026-08-05・提案②）

> **状態: 提案（未実装）**。採用先実測の監査で露出した欠陥への対策3件のうちの1件。
> 実装時に §10 の Phase として採番し、本文書へ実施結果を追記する。

## 背景

採用先の実測で「**散文の契約主張とコードの乖離**」が 2 型露出した:

- (a) インベントリ文書の「soft で全て不発」という過大主張が実装と食い違い、機械検査は
  素通し・**人力監査だけ**が捕捉した。
- (b) カバレッジ帳簿のプローブ集合が本番検出器の追加に追随せず、帳簿上の値が古いまま
  になった——検査は「宣言されたもの」を守るが「宣言域の欠落」に盲目。

キットは `gates-registry-drift`（Phase 45・hard）で台帳⇔検査器の**ID の存在**を
双方向照合済みだが、照合対象は ID のみ。**severity（hard/soft）は台帳の説明文に
「(soft)」と散文で書かれ、機械照合されていない**——キット自身の台帳の中に、今回
採用先で事故になったのと同型の「未照合の契約主張」が残っている。まず自分の台帳から
塞ぐ。

## 方針（規約 1 行の追加）

§3.3 の「新しい規則を足す時のレシピ」に次を追記する:

> 機械検査の相方を持たない契約主張（hard/soft・発火条件・不発条件）を散文にだけ
> 書かない。主張は構造化台帳（`GATE_REGISTRY`）の列へ昇格させ、台帳は双方向照合の
> 対象にする。散文は台帳への参照に留める。

採用先で有効だった「二分契約表」（各契約主張に検査の相方を対で並べる表）の
キット側の一般化がこれに当たる。文書の書式規約（§4）が「機械検査なし」と正直に
境界を引いたのと対照的に、**severity は判定列が書ける**——書けるものは門にする。

## 設計

- `GATE_REGISTRY` のタプルに **severity 宣言列**を追加する（5 列目）:
  - `"HARD"` / `"SOFT"` — 通常の検査規則
  - `"HARD→SOFT"` — 降格パスを持つ規則（kit-source-exempt で降格される
    `missing-required` / `agents-import-missing` 等）。両 severity の emit を許す。
  - `"-"` — emit を持たない行（`hook:` / `static:` 型）。照合対象外。
- 既存の `_GATE_EMIT_PATTERNS`（check_structure.py:136）は severity を**非捕捉**群
  `(?:HARD|SOFT)` で読み飛ばしている——これを捕捉に変え、実装から
  `(severity, 規則ID)` 対を収集する。台帳宣言との不一致は
  `HARD:gates-severity-drift`（2 方向: 宣言に無い severity で emit している／宣言した
  severity の emit が実装のどこにも無い）。
- **hard 直行**とする。比較は台帳とソースの両方がリポジトリ内で完結する決定的な
  文字列照合であり、偽陽性の構造的余地が無い（GOALS 非対称閾値①相当——soft で
  実測する不確かさが存在しない）。
- `dev.py gates` の一覧表示にも severity 列を出す（台帳が発見導線である以上、
  hard/soft は一覧で見えるべき情報——G4）。

## 対象外として明記する範囲

- **§3.3 散文の hard/soft 節配置との照合はしない**。散文のパターン照合は書式の固定化
  （＝事実上の第二台帳）を生む。方針は逆で、**照合したい主張を散文から台帳へ寄せる**。
- 主張の「真偽」一般（例:「この検査は◯◯を防ぐ」）は機械判定の境界外のまま
  （§2e・GOALS 前文の境界宣言どおり）。本提案が塞ぐのは判定列が書ける severity のみ。
- 採用先固有の帳簿（カバレッジ行列・プローブ集合等）の追随検査は、帳簿の構造が
  採用先ごとに違うため本体にハードコードしない（`doc-impact-undeclared` の対応表と
  同じ判断——2026-07-28 plan 参照）。該当構造を持つ採用先の列として個別に検討する。
