# doc-impact-undeclared: doc更新漏れの検出（2026-07-28）

> **実施結果（同日・v2.63・Phase 64）**: 下記方針のまま実装済み。詳細は
> `.guardrails/GUARDRAILS.md` §3.4 検査9・Phase 64。

## 背景

文書のHTML化（§4 文書書式規約・v2.62）とは別に、「利用者影響のあるソース変更をしたのに
対応する文書を更新し忘れる」という事象は、既存のどの検査（fix⇔テスト・feat⇔plan・
governance-without-goal）も拾わない空白だった。doc の陳腐化は commit の diff に出ない
ため、コード側の変更を起点にした検査では原理的に検出できる範囲が限られる（下記「対象外」
を参照）。

## 検討した2案

1. **グローバルパターン案**: 「`scripts/` 等の指定フォルダが変わったら、指定した doc の
   どれかが変わっていること」を1本のルールで判定する。実装は軽いが、無関係な doc を
   1文字触るだけで通る／doc 不要な内部修正（空白調整・変数リネーム）のたびに鳴ってしまい
   儀式化する。
2. **対応表案（採用）**: 「このソース群が変わったら、この doc 群」という source→docs の
   ペアを複数持つ。ペアごとに判定するため無関係な doc では通らず、対応の意味を label に
   書くことで違反者がラベルだけで直せる（G4）。

対応表案を採用。理由は feat-without-plan（`PLAN_LAYER_ROOTS`）と同型——「対応表は
プロジェクトごとに違う」という性質そのものが、キット本体にハードコードしてはいけない
ことを意味する。ハードコードすると、対応表の実パスが導入先ごとにずれ、「一度も発火しない
検査」になる（このリポジトリの検討過程で、他プロジェクト向けの対応表案をそのまま流用
しかけて発覚した失敗——README_SETUP.html 等このリポジトリに実在するパスを、別プロジェクト
の `engine/src`・`CURRENT_TRUTH.md` 等に書き換える提案が出たが、検証の結果それは
このリポジトリではなく別の採用先の話だと判明した）。

## 設計

- `bindings/catalog.md` の列充填値として `DOC_IMPACT_RULES`（`repo_scan.py`）を追加。
  空リストが既定値——列が空なら不発（`PLAN_LAYER_ROOTS` と同じ境界）。
- 各要素は `{"source": [正規表現...], "docs": [正規表現...], "label": "..."}`。
- 免除は本文の `DOCS-NOT-NEEDED: 理由`（存在検査のみ・理由の妥当性は検査しない——
  `NO-LOG:` / `RED-FIRST-EXEMPT:` と同じ境界）。
- **soft 導入**。対応表の粒度（広すぎる source・狭すぎる docs）は採用先の実測でしか
  検証できず、偽陽性が鳴りっぱなしだと「無視される hard」になり soft より悪い。
  feat-without-plan と同じ非対称閾値（`.guardrails/GOALS.md` 運用ルール）に従い、
  実測で偽陽性率を確認してから hard 昇格を判断する。
- 免除の乱用監視は専用機構を新設せず、既存の保留「免除・接頭辞の乱用点検指標」に合流
  させる（重複登録しない — G5）。

## 対象外として明記する範囲

この検査はソース側の diff を起点にするため、次の型は構造的に拾えない:

- コードを変更していないコミットで、文書内の記述が現実（実装・過去の結論）と食い違って
  いく型（撤回済みの結論が残り続ける・状態欄が実装とずれる 等）。
- この型を塞ぐには、特定の文書ジャンル（訂正・撤回を書く文書）と正本台帳の同時更新を
  対で強制する別の検査が要る。このリポジトリには該当するジャンルの文書構造が無いため
  今回は実装しない——採用先で該当構造（訂正を書くジャーナル文書＋正本台帳）が実在する
  場合に、その採用先の列として個別に検討する。

## 適用範囲

このリポジトリ自身の `DOC_IMPACT_RULES` は空のまま出荷する（`TEST_PATH_PATTERNS` /
`PLAN_LAYER_ROOTS` など他の列充填変数と同じ扱い——キット原本は自分の列を埋めない）。
採用先が bindings/catalog.md の運用に従い、自分のソース構造とdoc構造で列を起こす。
